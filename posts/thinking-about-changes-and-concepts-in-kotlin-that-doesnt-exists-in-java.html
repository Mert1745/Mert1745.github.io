Thinking about changes and concepts in Kotlin that doesn't exist in Java

May 17, 2024

Starting a Kotlin project at adesso Turkey, I explored what Kotlin offers that Java doesn't, to understand the thinking behind the language.

Functional and OOP. Kotlin supports both styles. Top-level functions and data classes can live in one file, reducing the number of files and classes needed for simple utilities.

Less boilerplate. Writing less code is appealing, but does it always improve speed or readability? Separating everything into files still feels more natural to me.

Type inference. Kotlin encourages val and var over explicit types. I find this less readable, since you must check the declaration to know the type.

Immutability and null safety. Values are immutable by default and nullability must be declared with ?. A well-considered, fail-safe design.

No checked exceptions. This surprised me. Checked exceptions often lead to verbose try-catch blocks and don't work well with inheritance or lambdas, so Kotlin's choice makes sense, though Java's position is less clear-cut than I assumed.

Kotlin suits modern, fast-changing requirements such as AOT compilation and mobile backends, and is worth adding to a developer's toolkit. Kotlin or Java depends on the use case.
